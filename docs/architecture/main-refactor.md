# Main 책임 분리 기록

## 기준과 문제

기준 커밋 bcb7240: main.gd 12,785줄, 함수 529개, 인스턴스 상태 399개, 신호 연결 137곳, await 2곳, SceneTree 타이머 3곳. 전체 파일을 함수/상태/호출 단위로 정적 분석하고 진입·입력·프레임·저장·통신 코드를 별도로 대조했다.

- 전투, 선택, 화면, 저장, 계정, 대기방과 네트워크 패킷이 한 객체의 필드를 직접 수정한다. 상태의 작성자를 찾기 어렵고 UI 변경이 게임 진행에 영향을 줄 수 있다.
- _process는 UI 배치 → 대기방/통신 → 연출 → 입력/상태 → 시뮬레이션을 순서대로 실행한다. 모듈마다 _process를 등록하면 순서가 달라진다.
- Main을 받은 Tower/Orb/Zone/CardDock/TutPlay도 많은 내부 메서드를 호출한다. 이름만 옮기고 수백 개 프록시를 남기는 방식은 결합을 숨긴다.
- 창별 필드·배치 캐시·선택 제스처 상태가 판 전체 상태와 섞여 있다. 오브젝트/카드 설명의 여러 표시 경로와 준비/전투/복원 경로가 특히 민감하다.
- Mp는 화면 재시작 사이에 살아남는다. 예전 화면의 신호를 끊고 재연결해야 한다. Net/Updater/PatchNotes는 씬 자식이지만 RefCounted 컨트롤러의 강한 역참조는 별도 누수 원인이 된다.
- 랜덤 시퀀스, 온라인 패치 숫자 키, 저장 키/판 형식, 멀티 메시지·재접속 순서가 외부 계약이다. 이 작업에서 변경하지 않는다.
- 기존 코드의 await/타이머는 계정 데이터 삭제·특성 길게 누르기 등 UI 생명주기에 묶여 있다. 실행 노드와 시간 기준을 유지한다.

## 선택한 구조

엄격한 계층형 구조는 모든 UI와 Godot 노드에 포트를 추가해야 한다. 순수 Feature 구조만으로는 공통 시뮬레이션·판 상태를 중복시킬 위험이 있다. 기능 컨트롤러 + 세션 계약을 사용한다.

- main.gd: Godot 진입·입력·프레임·그리기 콜백 연결.
- app/session.gd: 씬/판 공통 상태, 초기화 순서, 기존 공개 정적 계산/온라인 패치 상수 계약.
- app/feature.gd: 세션의 WeakRef. 컨트롤러는 프레임·입력 콜백을 스스로 등록하지 않는다.
- features/: 입력, 카드, 전투, 생성, 진행, 저장, 각 UI/외부 연동별 책임. 한 기능에서만 쓰는 필드와 제스처 상태는 해당 기능으로 이동한다.
- 기존 소비자는 main.feature_system.method로 명시적으로 연결한다. 기존 이름을 흉내 내는 동적 _get/_set 또는 대량 프록시는 만들지 않는다.

세션은 아직 공유 계약이다. 따라서 이 구조를 완전한 도메인 격리나 Clean Architecture 완성으로 부르지 않는다. Godot 노드·Rules/Meta 등의 기존 전역 계약을 유지하면서 상태의 소유권과 호출 경계를 먼저 명확하게 만든다.

## 단계와 검증

1. 기준 분석·동작 보존 기준 기록. 되돌림: bcb7240.
2. UI/온라인 보조 기능의 컨트롤러와 전용 상태 분리. 기능 명세·파싱·생성 자료 일치 검사 후 커밋.
3. 카드·입력·진행·저장과 전투·렌더링을 각각 후속 그룹으로 분리. 매 그룹 명세 검증, 마지막에 입력 E2E·이어하기·튜토리얼·fuzz·온라인 검사.
4. 최종 의존성·공개 계약·씬 재초기화·화면과 성능 확인. 각 단계는 직전 검증 커밋으로 되돌릴 수 있다.

변경 전 check: 명세 238개·튜토리얼·이어하기 4/8/12·온라인·패치 표 통과. fuzz 최초 4시드 중 2번에서 오류 2개, 동일 4시드 재실행은 모두 0개. 서버 Python 개발 의존성 없음으로 서버 테스트 건너뜀. TypeScript/ESLint는 이 Godot/GDScript 프로젝트에 해당하지 않음.

## 보존과 자체 리뷰

- 원래 함수 529개가 모두 소유 모듈에 존재한다. 참조 경로·동기 메서드의 세션 캐시를 정규화한 비교에서 522개의 문자열·숫자·연산·분기·호출 순서가 같다. 7개는 초기화 신호 범위, 배치 규칙 추출, await/타이머 뒤 씬 해제 방어를 명시적으로 검토했다. 기준은 `main-boundaries.json`, 도구는 `tools/architecture_audit.py`다.
- RefCounted 컨트롤러는 직접 프로세스/입력을 등록하지 않는다. 기존 루트 하나에서 처리 순서를 유지한다. draw도 원래 CanvasItem에서 실행한다.
- Node 버튼·draw 연결은 Node와 함께 해제된다. Net/Mp/Updater/PatchNotes 연결은 기존 등록 순서를 유지하면서 씬 종료 시 명시적으로 끊는다. 기존 Mp 재부모화/방 유지 흐름도 유지한다.
- await와 타이머의 시간·횟수는 변경하지 않았다. 늦게 끝나는 계정 삭제·신고·길게 누르기·추방 콜백에는 씬 생존 확인을 추가했다.
- 내부 메서드/상태 API의 소비자 51개 파일을 명시적 기능 경로로 갱신했다. `main.tscn`, 저장 형식·키, 멀티 메시지, `Main.*` 온라인 패치 키는 유지했다. 임의의 외부 스크립트가 사설 `main._method`에 의존하는 계약까지 보장하지 않는다.
- 카드 지연 호출의 문자열 경로 2곳도 이전했다. 일반 메서드 호출만 검사할 때 빠졌지만 fuzz가 잡았고, 감사 도구에 오래된 동적 호출 경로 검사도 추가했다.
- 상속/프리로드를 기능끼리 사슬로 엮지 않았다. 하지만 런타임 협력 그래프에는 21개 기능의 강연결 묶음이 남아 있다(`collaboration.json`, 212개 방향 연결). 이는 해소됐다고 주장하지 않는다. 기능 간 협력과 수명 참조 순환은 별개이며, 수명 순환은 WeakRef/해제 검사로 확인한다.
- 통계 표본 검사 MAPX-01은 앞선 UI/소리 타이밍의 RNG 소비에 영향받아 경계에서 실패할 수 있었다. 표본 추출 직전에 시드를 고정해 검사 간 순서 의존성을 줄였다. 게임의 랜덤 로직은 바꾸지 않았다.
- 전체 검사 로그를 고정 `/tmp/bindu_check_*`에 쓰던 충돌 위험도 제거했다. 이제 `mktemp`로 실행별 로그 디렉터리를 사용하며 실패 시 경로를 남긴다.

## 검증 결과와 범위

- Godot 4.7.2 파싱 및 실제 초기화, 명세 238개, 플레이 튜토리얼, 4시드 × 3,000프레임 fuzz, 4/8/12웨이브 저장 복원 후 13웨이브 도달, 온라인 mock 및 패치 키/표 일치 검사를 실행했다.
- 서비스 중복 구독/씬 종료 해제, 독립 씬 상태, 소유 씬 해제 후 컨트롤러 생존, 서비스 재연결/해제, 순수 배치 경계값을 `tools/run.sh architecture`에 추가했다.
- PC 130%의 사용성 통합 시나리오(선택/미선택 우클릭·드래그·방향 확정/취소·카드 우선순위·일시정지·소유권·특성 등)는 실패 0/UI 진단 0.
- 폰 안전 영역 130% carry 검사는 변경 전과 후 모두 실패 9개·제목 잘림 진단 1개이며, 실패 문구 10개가 동일하다. 기존 검사 실패를 통과로 표기하지 않는다.
- PC 100%·130%, 폰·태블릿 터치 130% 전체 화면 캡처를 실행했다. 최종 진단은 각 조건에서 변경 전 진단 집합의 부분집합이며 신규 진단은 없었다. 기존 넘기기 배지/기술 버튼/인스펙터 겹침은 남아 있다. 프레임 시각·호버에 의존하므로 픽셀 동일성의 증거로 사용하지 않는다.
- CPU 표본: 12오브젝트·200구체, 시작 이후 시드 7, 준비 60조각 후 240조각, 3회 교차 실행. 기준 평균 약 0.574ms → 분리 후 약 0.620ms(약 +0.046ms, +8%). 이 소규모 CPU 경계 비용은 남아 있으며 성능 동등으로 보고하지 않는다. 고정 시드여도 기존 실제 시계/소리 제한 때문에 피해 합은 완전히 고정되지 않는다.
- 기존 후반 perf는 x1/x4까지 관찰했지만 동시 부하·구체 수가 달라 엄격한 비교에 쓰지 않았고, 장시간 x8은 완료하지 않았다. 렌더링/GPU·실기기·실제 서버/다중 기기 멀티 성능은 검증하지 않았다.
- ObjectDB 종료 경고 2개는 기존 native UI 검사와 분리 후 모두 관찰된다. 이를 새 구조에서 누수가 완전히 없어졌다는 증거로 해석하지 않는다.
- 서버 Python 테스트는 fastapi/pytest/httpx 부재로 건너뛰었다. TS/ESLint는 해당 없음. 배포·push는 하지 않았다.

## 남은 개선 우선순위

1. 공유 세션 상태 259개와 21개 기능의 상호 호출을 더 작은 읽기/쓰기 계약으로 줄인다. 저장 복원과 전투 전환처럼 순서 민감한 경계부터 진행한다.
2. 수치/카드 카탈로그와 Meta/Rules 전역 접근을 값 스냅샷으로 전달해 규칙 테스트의 전역 오염을 줄인다.
3. 메뉴·전장 그리기는 여전히 1,000줄 이상이다. 다음 분리는 실제 UI 책임/생명주기 기준으로 하고 위젯마다 파일을 만드는 방식은 피한다.
4. CPU 경계 비용, 실제 시계에 따른 RNG 소비, 기존 ObjectDB 경고의 소유 경로를 독립 프로파일로 더 좁힌다. 실기기/GPU 검증도 필요하다.
5. 기존 폰 carry 실패와 넘기기/인스펙터 겹침은 기능 수정 작업으로 별도 처리한다.

오브젝트 인스펙터의 `attack_preview.gd`는 독립 World2D의 BinduSession에서 실제 전투 로직을 재사용한다. 미리보기 처치는 전투 효과만 실행하며 보상·업적·저장을 실행하지 않는다. 별도 조합 창은 인스펙터로 통합했다.

미리보기는 주변 오브젝트와 누적 발동 상태까지 복제하고 실제 월드 좌표를 유지한다. `BinduCombat.step_entities`와 `tick_effects`를 실제 전투와 공유한다. `tools/run.sh preview basic|pairs|deaths|context|long`으로 같은 시드·표적에서 실제 `_sim_step`과 프레임별 결과를 대조하며, `check`에는 기본·처치 검사가 포함된다. 전투 그림은 `preview_gallery.gd`로 별도 확인한다.
